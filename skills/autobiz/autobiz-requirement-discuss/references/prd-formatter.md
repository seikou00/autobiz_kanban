# PRD 格式化技能

根据用户上传的原需求，按照模板格式重写需求文档。

使用任何 `request_user_input` 前，必须先读取并遵循 `${pluginPath}/skills/references/ask-user-question.md`。

## 工作流程

### 步骤1：读取原需求文档

读取用户提供的原需求文档内容。

### 步骤2：读取模板文档

读取 `{pluginPath}/skills/autobiz/autobiz-requirement-discuss/references/prd_module.md` 模板文档，了解改写格式要求。

### 步骤3：分析原文档结构

分析原需求文档的内容结构，识别其包含的章节和内容类型（如背景说明、角色定义、功能描述、验收标准等）。**注意：模板文档的章节结构可能动态调整，应基于实际读取的模板内容而非硬编码的章节列表进行分析。**

### 步骤4：按模板重写文档

按照 `{pluginPath}/skills/autobiz/autobiz-requirement-discuss/references/prd_module.md` 模板格式，将原需求文档内容填充到对应章节。

#### 章节输出决策（权威规则）

必须先依据原文的章节、业务内容和用户确认输入，逐项决定模板章节是否输出；不得因模板存在某章节就自动填充。**本表为章节是否输出的唯一判断依据**：必填章节按表中规则生成，条件输出章节缺少明确原文依据时直接省略，不提问、不推测。

| 模板章节 | 输出条件与处理方式 |
| --- | --- |
| 背景、痛点、改进思路及价值 | 必须输出。仅根据原文的问题陈述、目标、现状和价值描述归纳生成；不得添加原文没有的业务事实、量化目标或解决方案。 |
| 用户角色表 | 仅当原文或用户补充明确给出角色及其说明时输出；否则省略。 |
| 术语名词解释 | 仅当原文或用户补充明确给出术语及其解释时输出；否则省略。 |
| 价值衡量指标 | 仅当原文或用户补充明确给出指标、计算规则、目标值或基准值时输出；否则省略。 |
| 用户现状 / 用户旅程图 | 必须输出。基于原文中的角色、现状、业务流程和问题生成；某个旅程维度无明确依据时标记“【待确认】”，不得虚构。 |
| 用户故事地图或流程图 | 必须先由用户选择其一；再根据原文和用户确认输入生成，不得同时输出两者。 |
| 状态图 | 仅当需求明确涉及状态、状态转移、触发条件或生命周期时输出；否则省略。 |
| 角色与权限矩阵 | 仅当需求明确涉及多个角色且角色之间存在不同权限、操作范围或可见范围时输出；否则省略。 |
| 原型设计图 | 仅当原文或用户补充提供 UI、页面说明或高保真链接时输出；存在链接/路径时登记链接/路径，仅有 UI/页面说明时保留其原文说明；否则省略。 |
| 功能清单与功能详情 | 必须输出。按原文功能章节拆分 FR；功能详情以原文为主体，逐段、逐表、逐列表保留业务细节和验收项，并保持易读。 |

**子步骤说明：**

#### 4.1 询问用户选择方案设计类型

使用 `request_user_input` 询问用户选择方案设计类型：

此为模板规定的固定必经输入，不属于“功能清单/功能详情”信息缺失时的澄清提问；即使原文信息完整，也必须执行。

**问题ID**: design_type
**问题**: 请选择方案设计类型
**选项**:
1. 用户故事地图 - 适用于复杂产品需求梳理，通过地图避免遗漏关键模块，并产出版本发布计划
2. 流程图 - 适用于步骤明确的流程，将复杂流程简化、逻辑清晰化

先根据原需求判断更适合的类型，将该选项放第一位并在 label 末尾标记 ` (Recommended)`；不得固定推荐某一种类型。

#### 4.2 生成用户旅程图

根据原需求文档的内容，分析并生成用户旅程图，包含：
- 用户角色：基于原文档中涉及的岗位
- 旅程阶段：基于原文档的核心交付和功能流程
- 触点：用户与系统交互的具体环节
- 用户行为：在每个阶段的具体操作
- 痛点与机会点：从原文档中提取的改进点

#### 4.3 填充模板各章节

将原需求文档内容按模板章节结构逐项填充。

**重要规则：**
- “用户角色”“术语名词解释”“价值衡量指标”仅在原始需求文档或本次用户补充中存在明确内容时输出；无明确内容时可为空，不得从页面使用人、权限信息、业务名称、需求目标或其他上下文自行推导、补充。
- 对“用户角色”“术语名词解释”“价值衡量指标”缺少明确内容的情况，不得发起澄清或提问；仅当用户主动补充或原文明确给出时再填写。
- 模板中的流程图、状态图、角色权限矩阵和价值指标均不是允许扩写原文的依据：其中的每个业务事实必须能追溯到原文或用户确认补充。没有来源的“痛点/机会点”、指标目标值/基准值、角色权限、状态分支和实现机制不得生成；或省略该视图。
- **生成的新PRD中禁止包含模板文档的注释说明内容**（如"> 1. **描述**：..."、"> 2. **核心要素**：..."、"> 3. **适用场景**：..."、"> 4. **局限性**：..."等模板编写说明）
- 只保留模板的章节结构框架，具体的填写内容应基于原文档分析得出

##### 4.3.1 功能详情保真、格式保留与功能原子要求清单

处理“功能清单/功能详情”前，建立“功能原子要求清单”。该清单**仅覆盖原文功能清单及其 `R/FR` 功能说明**中的每一项可独立验证的要求，至少包括：字段行、表格行、编号规则、枚举值、限制数值、提示文案、状态条件、外部协作规则和验收项。保留其原文、来源位置和所属业务上下文；背景、术语、价值指标、用户旅程图等非功能说明内容不纳入该清单。

**功能详情生成与格式保留**

每个 `FR` 的“功能详情”必须以原文中对应的 `R/FR` 章节为主体，按原始顺序**逐条、完整复刻**业务规则、字段说明、按钮说明、权限规则、流程、异常处理和验收标准。原文事实只能忠实重排版；用户确认补充必须记录确认轮次/日期和来源；未经确认的推测、最佳实践和实现建议不得写入需求摘要。

- 保留原文的标题层级、章节顺序、段落、表格、列表、代码块、字段分组、编号及强调方式。表格继续以表格呈现，列表继续以列表呈现；允许的变换仅限于补充模板外层章节、调整 Markdown 语法、统一明显的标题/空行格式和增加 FR 定位。
- `功能概述` 仅提供入口、范围等导航信息，不能摘要、替代或重复原文功能说明；原文已有子标题时保留，原文无子标题时不得凭空细分。
- 仅当原文无结构、存在明显歧义或必须拆分到多个 FR 时才可重组；仍须保留原始顺序和视觉分组，在映射表说明原因，并在每个相关 FR 保留完整上下文与共用前置条件。
- 不得为了简洁、美观或标题统一而改写用户可见文案、合并规则、调整规则顺序或新增解释性内容。
- 接口/附件引用及 Markdown 链接必须保留链接文字和目标地址；字段全称、枚举值及其解释、状态名称、提示/通知文案、变量占位符、日期/编号格式和示例值必须逐字保留。不得缩写、同义改写、删除限定词或将多个条目概括为一句话。
- 原文功能子标题及其内容块必须一一保留。状态定义表、流程图/流程步骤、状态转移规则是不同类型的信息：原文以表格定义状态时必须保留原表及每行说明，不得用推测的状态箭头替代；原文未明确的转移关系不得补充。
- 同一功能中的不同业务场景必须分别保留，例如单笔/批量、冻结/解冻、成功/失败、不同角色或不同系统处理结果；不得以“按场景区分”“根据情况处理”等概括性文字替代原始条目或模板。
- 跨系统联动必须完整保留触发时机、前置条件、调用目标、成功/失败分支、后续动作和记录/提示文案。适用角色、权限范围和可跳转范围仅在原文明确时输出，不得新增“所有用户”等泛化结论。
- 原文验收标准必须在对应 FR 的“验收标准”中逐项原样保留；不得合并、删除或以功能概述中的描述替代。

##### 4.3.2 功能原子要求映射、核查与澄清

在交付前对原文功能清单/功能详情与生成 PRD 进行双向核查，并输出或保留可审计的“功能原子要求映射表”。映射表至少包含：功能原子要求编号、原文/来源位置、要求类型、目标 FR 编号、生成 PRD 中的具体位置、核查结果。

映射表还必须保留“原文要求”列，摘录能用于核验的关键原文。仅映射到 FR 标题、功能概述或“已纳入”均为无效映射。

核查规则：
- 原文功能清单/功能详情中的每一个功能原子要求都必须存在至少一条有效映射，且该映射指向对应 FR 的具体说明位置。
- 逐项核对原文与生成内容，确认字段行、表格行、编号规则、枚举值、限制数值、提示文案、状态条件、外部协作规则和验收项均未遗漏、篡改或弱化。
- 对接口/附件链接、字段全称、枚举解释、提示/通知文案、变量占位符、日期/编号格式和示例值做逐项文本核对；链接文字和目标地址、字段/文案原文必须一致。
- 反向检查每个 FR：其中新增的业务规则、数值、枚举、状态、提示文案和验收标准必须能追溯至原文，或明确标注为经用户确认的补充；不得将未经确认的推测写为既定需求。
- 对用户旅程图、流程图、状态图、权限矩阵、价值指标逐项做同样的反向核查；这些视图不允许出现无来源的事实或数值。
- 对每个功能详情进行可读性回检：表格、列表、字段分组和规则顺序须与原文等价且易于扫描；若格式转换使层级更深、重复更多或定位更困难，应恢复为原文的展示方式。
- 逐个对照原文 `R/FR` 章节与生成的对应 FR，确认其正文可以独立阅读并完整还原原文功能说明；不得只核查功能原子要求映射表或摘要。
- 发现未映射、映射不具体、内容冲突或无法确认的功能原子要求时，不得静默省略；应在改写过程中向用户澄清，并在完成前关闭所有问题。

**交付门禁：** 只有全部功能原子要求均存在有效映射、所有生成事实均可追溯，且不存在功能细节遗漏、弱化、冲突、无来源扩写或可读性下降时，才可将结果写入/更新 `PRD_DISCUSS.md` 并继续后续流程。任一核查失败时，格式化结果视为未通过：应恢复原文的展示结构、修正功能原子要求映射，或将无法确认的内容标为“【待确认】”并向用户澄清；不得交付不合格输出。

仅在**功能清单/功能详情**中的字段、规则、流程、验收项或业务逻辑找不到对应内容，且不能以“【待确认】”保真呈现时，使用 `request_user_input` 向用户澄清。

其他模板章节没有明确内容时，按“章节输出决策”直接生成或省略；不得为此提问或推测填充。


## 模板章节说明

**注意：以下章节结构基于当前模板文件 `{pluginPath}/skills/autobiz/autobiz-requirement-discuss/references/prd_module.md` 的内容。模板可能动态更新，实际重写时应以模板文件的最新内容为准，不要在生成的新PRD中包含模板的注释说明。**

当前模板包含以下章节结构：


**需求摘要**

1. **需求概述**
- 1.1 背景、痛点、改进思路及价值（必填）
- 1.2 用户角色表（条件输出）
- 1.3 术语名词解释（选填）
- 1.4 价值衡量指标（选填）

2. **需求解析**
- 2.1 用户现状（必填，含用户旅程图）
- 2.2 方案设计（用户选择：用户故事地图 或 流程图）
- 2.3 状态图（条件输出）
- 2.4 角色与权限矩阵（条件输出）
- 2.5 原型设计图（条件输出）
- 2.6 功能清单（必填）
  - 2.6.1 功能详情（每个功能FR1、FR2...）

## 注意事项

- “用户角色”“术语名词解释”“价值衡量指标”为条件输出项：仅输出原始需求文档或本次用户补充中明确提供的内容；没有特殊明确内容时允许留空，禁止根据页面使用人、权限、业务名称或需求目标推导、补全或提出追问。
- 功能清单是必填项，必须完整包含原文档中的所有功能点
- 每个功能需要包含功能概述和验收标准
- 验收标准需要详细完整，不遗漏原需求文档中的任何细节
- 生成的新PRD中禁止包含模板的注释说明，只保留章节结构和实际业务内容
- 用户旅程图必须根据原文档内容生成，不能留空或复制模板注释
- 方案设计必须先询问用户选择类型，再根据选择生成对应内容
