# autodev-plan 探索样例

`/autodev-plan` explore 阶段的示范素材：ASCII 可视化模板 + 不同切入点的对话样例。按需查阅即可，核心探索姿态、结束门与约束仍在 `SKILL.md`。


## 处理不同的切入点

**用户带来一个模糊的想法：**
```
用户：我想做一个审批提醒

你：审批提醒可能涉及通知时机、接收人、渠道和幂等。先把边界拆开看一下：

      提醒范围
      ════════════════════════════════════════════

      触发时机             接收人              渠道
          │                   │                 │
          ▼                   ▼                 ▼
      ┌────────┐         ┌────────┐        ┌────────┐
      │提交后  │         │审批人  │        │站内信  │
      │超时前  │         │抄送人  │        │短信/邮件│
      │退回后  │         │发起人  │        │Webhook │
      └────────┘         └────────┘        └────────┘
          │                   │                 │
       影响任务           影响权限           影响接口/配置

      specs 里目前明确了哪几项？哪些需要我回到代码里查现有通知能力？
```

**用户带来一个具体问题：**
```
用户：这个导出需求不知道怎么拆任务

你：[读取代码库]

     ┌─────────────────────────────────────────────┐
     │              当前导出链路                     │
     └─────────────────────────────────────────────┘
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
     ┌─────────┐  ┌─────────┐  ┌─────────┐
     │ 查询参数 │  │ 权限校验 │  │ 文件生成 │
     └────┬────┘  └────┬────┘  └────┬────┘
          │             │             │
          └─────────────┼─────────────┘
                        ▼
                  ┌───────────┐
                  │  下载响应  │
                  └─────┬─────┘
                        │
                        ▼
                  ┌───────────┐
                  │  审计日志  │
                  └───────────┘

     我看到四个需要确认的边界：导出字段、权限范围、文件大小、失败重试。
     我先把这些作为 Plan 的待确认项，还是你现在补充一下？
```

**用户在实施过程中卡住：**
```
用户：/autodev-plan --feature export-orders
      导出接口到底要不要支持异步

你：[读取 proposal、specs、现有导出模块、已有 design.md/plan.json]

     当前 specs 只写了“用户可以导出订单”，没有说明数据量上限。
     代码里已有一个同步 CSV 导出，但超过 5 万行会超时。

     我建议把这里作为待确认决策：
     - 小数据量：同步下载
     - 大数据量：异步任务 + 下载链接
     - 未确认：阈值、通知方式、文件保留时间

     要不要按“先同步、标注异步为待确认风险”的方式生成 design.md 和 plan.json？
```

**用户想要比较选项：**
```
用户：这个配置是写数据库还是配置文件？

你：先看使用场景和现有项目习惯。

用户：运营后台里配置一个导出字段白名单

你：这个场景更像运行时业务配置，不只是部署配置。

     ┌─────────────────────────────────────────────────┐
     │          字段白名单存储方式对比                  │
     └─────────────────────────────────────────────────┘

     关键约束：
     • 运营可能随时调整
     • 需要权限和审计
     • 需要灰度或回滚

                  数据库          配置文件
     动态调整      支持 ✓          需发布 ✗
     审计          易支持 ✓        需额外机制
     回滚          可记录 ✓        依赖发布流程

     我倾向数据库方案，但会把字段、权限、审计作为待确认点进入 design.md/plan.json。
```
