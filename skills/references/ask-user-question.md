# 用户澄清与 `request_user_input` 统一协议

所有需要用户选择、确认或补充关键信息的技能统一遵循本协议。业务技能负责定义要确认的业务内容，本文件负责约束提问时机、原生工具结构和回答处理。

## 1. 判断是否需要提问

仅在以下情况提问：

- 存在会改变范围、行为契约、实现路径、验收结果或外部动作的关键歧义。
- 缺少用户偏好、约束或授权，且无法从现有材料、代码或状态中可靠确定。
- 工作流明确要求用户做阶段门、状态或方案选择。
- 用户明确要求“先问我”“澄清”“访谈”或类似交互。

以下情况不要提问：

- 可从项目文件、状态脚本或已有对话中查明。
- 有安全、可逆且不会改变用户意图的默认值；直接采用并说明假设。
- 只是为了汇报进度、重复已经回答的问题，或让用户确认无关紧要的细节。

提问前如上下文较复杂，用 1–2 句话复述当前理解，并说明这次选择会影响什么；简单阶段门可直接提问。每轮只问继续推进所必需的问题。

## 2. 优先使用原生工具

当前运行模式支持 `request_user_input` 时优先使用它；不支持时按“文本降级”处理。调用原生工具时严格遵守：

- 每次传入 1–3 个 `questions`；超过 3 个问题时按优先级拆成多轮。
- `header` 不超过 12 个字符，只作为短标签。
- `id` 使用稳定的 `snake_case` 键；同一决策跨轮次保持不变。
- `question` 用一句话描述需要用户做出的决定。
- 每题提供 2–3 个互斥 `options`，推荐项放第一位，并让其 `label` 以 ` (Recommended)` 结尾。
- 每个选项的 `description` 用一句话说明选择后的影响或适用条件；附件中的 `why_it_matters` 应融入这里或提问前的复述，不要发送工具不支持的字段。
- 不要手工添加 `Other` / “其他”选项；客户端会自动追加自由输入入口。
- 只有问题不阻断工作、未回答时可以安全采用推荐项继续，才设置 `autoResolutionMs`（60000–240000）。需要明确选择、授权或阶段门确认时必须省略该字段并等待用户。
- 工具调用本身已经表达暂停，不再额外输出“Questions”标题、手写问卷或“请回答后我再继续”。

标准调用形态：

```json
{
  "questions": [
    {
      "header": "阶段确认",
      "id": "next_step",
      "question": "是否结束探索并进入 Plan 生成？",
      "options": [
        {
          "label": "进入 Plan (Recommended)",
          "description": "当前结论已足够，将开始生成设计与执行计划。"
        },
        {
          "label": "继续探索",
          "description": "保留当前阶段，继续补充或修正关键决策。"
        },
        {
          "label": "暂不生成",
          "description": "停在现有澄清结果，不创建后续产物。"
        }
      ]
    }
  ]
}
```

## 3. 需要用户填写自由文本时

链接、文件路径、联系人、配置值、补充说明等内容必须由用户实际填写，不能靠选择一个预设选项完成。遇到这类问题时：

- 在 `question` 中一次性说明：若现在可以提供，请直接在客户端自动提供的 Other /「其他」输入框填写具体内容。
- 仍须提供 2–3 个互斥 `options`，不得因为希望用户填写 Other 而省略选项。预设选项只表示“不填写具体内容时如何处理”，通常使用“后续补充并继续”和“缺少该信息前暂停”；只有业务上确实成立时，才可把第二项换成“不适用”。
- 禁止把“现在提供”“提供路径”“补充说明”等需要后续输入才能完成的动作设为预设选项。用户选择这类空动作后再发起一次询问属于重复提问。
- 用户通过 Other 填写的内容就是该问题的完整回答，应直接吸收并继续，不得再询问一次相同内容。
- 用户选择“后续补充并继续”后，将该项记为待确认并继续处理其他问题；同一轮不得再次询问，除非后续步骤证明它已成为实际阻断项。

示例：

```json
{
  "questions": [
    {
      "header": "接口文档",
      "id": "api_doc",
      "question": "接口文档目前如何处理？若现在可提供，请直接在「其他」中填写文档链接或路径。",
      "options": [
        {
          "label": "后续补充并继续 (Recommended)",
          "description": "将接口文档记为待确认项，先继续讨论其他需求。"
        },
        {
          "label": "缺少文档前暂停",
          "description": "保留当前进度，拿到接口文档后再继续讨论。"
        }
      ]
    }
  ]
}
```

## 4. 候选较多时

- 问题超过 3 个：按阻断程度排序，每轮最多询问 3 个；收到回答并应用后再判断是否需要下一轮。
- 候选超过 3 个：先在提问前完整展示候选清单，工具中只放 2–3 个最相关候选；用户可通过客户端自动提供的 Other 输入清单中的其他值。不得静默丢弃候选。
- 逐项裁定数量较多：每轮最多处理 3 项，保持各项 `id` 稳定并记录已确认项，避免重复询问。

## 5. 文本降级

运行模式不支持 `request_user_input` 时：

- 用普通文本提出同一个最小问题，保留推荐项和各选项影响说明。
- 明确列出 2–3 个选项，并额外允许“其他（请说明）”。
- 阻断性问题必须停止等待答复；不要因为工具不可用而代替用户确认。

## 6. 处理回答并继续

- 预设选项与用户自由文本都视为有效回答；用户给出实质补充时吸收其内容，不要机械重复同一结构化问题。
- 使用稳定 `id` 在流程内部归一化答案，并立即应用到原任务、状态判断或目标产物。
- 只有回答缺失、互相矛盾或超出当前问题范围且确实阻断时，才针对该项再问一个最小追问。
- 用户拒绝选择且允许安全默认时，采用第一项推荐值并明确记录为默认；不能安全默认时继续等待明确答复。
- 不要为了展示流程而强制向用户输出 `user_answers` JSON。仅当下游脚本、状态文件或业务产物明确要求结构化记录时，才写出类似下面的对象；未知字段只在 schema 要求时填 `"unknown"`，不要凭空补固定字段。

```json
{
  "user_answers": {
    "<stable_id>": "<normalized_value>"
  }
}
```

完成回答处理后，显式基于已确认内容继续原任务；仍有阻断项时只追问剩余的最小集合。
