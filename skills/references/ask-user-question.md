# 用户澄清与 `request_user_input` 统一协议

所有需要用户选择、确认或补充关键信息的技能统一遵循本协议。

## 工具字段与回答处理

- 每轮 1–3 个 `questions`，每题包含简短 `header`、稳定的 `snake_case` `id`、完整的 `question` 和 2–3 个互斥 `options`；选项提供明确的 label 与 description，推荐项排在首位并以 ` (Recommended)` 结尾。
- 不要手工添加 `Other`，客户端自动提供自由文本入口。自由文本问题仍须提供 2–3 个互斥 `options`，表示确实成立的处理结果；禁止把“现在提供”“提供路径”“补充说明”作为空动作选项。在问题正文说明用户可以在 Other 中填写具体实体。
- 用户已经填写实质内容时直接吸收并继续，不得再询问一次相同内容。只补问仍缺失、且会影响当前任务的信息。
- 必须等待用户裁定的问题不设置 `autoResolutionMs`，超时与推荐项预选均不代表用户回答。工具不可用时才使用文本降级，保留问题和选项的原有语义。

## 未决条目的裁定

- 只裁定真正未决的条目；展示不等于裁定，已确认结论直接复用。`id` 按决策内容生成，不为重复展示新增决策。
- 裁定即消解：将具体方案或信息实体写入对应产物，再移除待确认标记。声称拥有 ≠ 提供；缺失材料可选择移除该依赖，或暂停，拿到材料后继续。
- 延后判定按语义不按字面。凡选中后条目仍处于待确认状态的选项都是非法选项；逐条裁定环节禁止使用延后类预设选项，包括「已准备好，稍后提供」。
- 不存在「先假设 / 先按默认方案 / 先占位」后推进的出口，不得以任何措辞重新引入。探索期的继续讨论选项禁止搬进裁定门。
- 完成裁定后做消解自查；仍缺少关键材料或具体结论时不能把条目标记为已确认。

##  候选较多时

- 问题超过 3 个：按阻断程度排序，每轮最多询问 3 个；收到回答并应用后再判断是否需要下一轮。
- 候选超过 3 个：先在提问前完整展示候选清单，工具中只放 2–3 个最相关候选；用户可通过客户端自动提供的 Other 输入清单中的其他值。不得静默丢弃候选。
- 逐项裁定数量较多：每轮最多处理 3 项，保持各项 `id` 稳定并记录已确认项，避免重复询问。
完成回答处理后，显式基于已确认内容继续原任务；仍有阻断项时只追问剩余的最小集合。
