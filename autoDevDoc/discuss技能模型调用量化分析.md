# autobiz-requirement-discuss 真实模型运行量化分析

- 样本：`session.json` + `raw_api_call.json`（协议授权 Feature，checkpoint `prd_in_progress → prd_done`）
- 模型：`deepseek-v4-flash-284b-a13b-w8a8`（W8A8 量化 MoE flash 模型，非 Claude）
- 结论先行：**74 次模型调用中 31 次（42%）、1070 万输入 token 中 548 万（51%）花在"最后一步校验失败后的返工"上**，根因是同一份 `PRD.md` 存在三份互相冲突的结构规格。

## 四、根因

### R1 同一个 PRD.md 有三份互相冲突的结构规格

| 来源 | 首行 | 要求的章节 | 禁止的章节 |
|------|------|-----------|-----------|
| `references/prd_module.md`（模板） | `# 需求摘要` | 1.需求概述 / 2.需求解析 / 2.6 功能清单 / 2.7 外部资料与实现约束 | — |
| `SKILL.md` §讨论沉淀生成 | 未规定 | 需求摘要 / 当前已确认结论 / 问题清单与处理状态 / **待确认事项** / 假设与风险 / **历次讨论记录** / 讨论补充资料 / 外部资料与实现约束 | — |
| `skills/autobiz/hooks/prd_rules.py`（校验） | `# 需求正式稿` | **用户故事 / 验收口径 / 验收标准 / 关键约束** / 外部资料与实现约束 | **历次讨论记录 / 待确认事项 / 审理提炼 / 外部依赖 / 第三方依赖** |

`# 需求正式稿`、`验收口径`、`用户故事`、`关键约束` 在任何技能文档、模板中都不存在——全仓库只出现在 `prd_rules.py` 和 `tests/`。模型只能去读 `biz_validate.py`（第 42 轮）和 `prd_rules.py`（第 43 轮）源码反推。

### R2 模板分支与校验规则存在结构性死路

`prd-formatter.md:41` 规定「用户故事地图 或 流程图 二选一，不得同时输出两者」，但 `REQUIRED_PRD_SECTIONS` 无条件要求 `用户故事`。**用户选流程图必然失败**，技能文档无任何提示。

### R3 校验只在终点跑一次，且与 checkpoint 循环依赖

`SKILL.md` 顺序是 `更新状态(prd_done)` → `输出清单校验`，而 `_check_done_checkpoint()` 要求 checkpoint 已是 `prd_done` —— "必须先声明完成，才能验证是否完成"。

### R4 报错不带修复方式

违反 AGENTS.md「脚本返回错误时应打印修复方式」的既有规定，直接导致 R1 的源码反推。

### R5 source-context.json 登记粒度超出模型手工能力

每份附件的每个表格行都要登记为 item，含逐字 `original`（必须能在快照中定位）。本次 4 份附件 = **112 个 item**。模型的实际行为是**自己写了一个 `_gen_source_context.py` 生成器**（调用 126→130，含一次 import 顺序 bug 调试），跑完再删掉。

### R6 大文件单次写入超出模型能力

重写正式稿时连续 3 次 `__cmbRecoveredMalformedToolCall__`（tool call JSON 截断），被迫降级为「分块写 `_chunk2/3/4.md` → `cat >>` → `mv` 覆盖 → `rm` 清理」，额外消耗 6 次调用。

### R7 交互协议过重 → 被整体跳过，且校验器反向激励

`SKILL.md` 规定 P0→P1→P2 逐项 `request_user_input`、每轮≤3 项、2–3 互斥选项……**实际全程只发起 1 次、1 个问题**。其余待确认项被模型自行消解后整章删除。而校验器把 `待确认事项` 列入 `FORBIDDEN_PRD_SECTION_TITLES` —— **删掉就能通过**，与 `SKILL.md`「禁止自行消解」直接冲突。

### R8 自查规则写成散文导致 N 次串行 grep

`SKILL.md`「消解自查」列了 8 个占位词，模型逐个 grep，产生 9 次调用、6 次 `No matches found`。
