# Batched Plan And Evidence Layout Design

## Goal

Keep long features auditable without loading every task into one Code conversation. Plan output is split into independently executable batches of at most five tasks, while evidence keeps one structured fact source and one real command log per validation attempt.

## Artifact Layout

All workflow artifacts stay under the feature artifact directory:

```text
.autobizdevops/features/<feature>/
  plan.json
  PLAN.md
  plans/
    B001/plan.json
    B002/plan.json
  evidence/
    EVIDENCE.jsonl
    EVIDENCE.index.json
    ev_0001.log
    .pending/
  .task-runs/
  BATCH_HANDOFF.json
```

`plan.json` is only the feature and batch index. It must not contain `tasks`. Each `plans/Bxxx/plan.json` owns at most five tasks. Task IDs remain globally unique across all batches.

`EVIDENCE.jsonl` is the only structured evidence fact source. New evidence does not create `ev_XXXX.json`; `ev_XXXX.log` contains captured command output only. Historical artifact-version-1 sidecars remain readable and auditable, but are never generated by the current writer.

## Batch Construction

Plan groups tasks by primary specification capability, then orders groups by task dependencies. A capability group larger than five tasks is split into consecutive batches. A batch may depend only on earlier batches. Cycles, forward dependencies, duplicate task IDs, and batches over five tasks are rejected.

The root index records:

- feature status and active/next batch IDs;
- batch order, task IDs, capability/spec roots, dependencies, and projected status;
- project-level validation commands and evidence IDs;
- `batchPolicy.maxTasks = 5` and `batchPolicy.strategy = spec_capability_topological`.

Each batch plan records task contracts plus batch status, counts, timestamps, and completion evidence IDs.

## Status Model

Feature statuses are `todo`, `in_progress`, `awaiting_next_conversation`, `failed`, and `done`. Batch statuses are `todo`, `in_progress`, `failed`, and `done`. Task statuses remain `todo`, `in_progress`, `failed`, and `done`.

Only tasks in `activeBatchId` may start or complete. Completing a non-final batch atomically:

1. marks the batch `done`;
2. updates its root projection;
3. sets feature status to `awaiting_next_conversation`;
4. clears `activeBatchId` and sets `nextBatchId`;
5. writes `BATCH_HANDOFF.json` with a compact summary and activation command;
6. returns a stop instruction to the Code skill.

The next conversation runs `task_runner.py activate-batch --batch-id Bxxx`. Activation verifies dependencies and consumes the handoff artifact. The Code skill must stop after emitting the handoff; it must not continue into the next batch in the same conversation.

After the final batch, project checks run separately. Their evidence has `action=project_check`, does not satisfy task acceptance criteria, and is required before feature status becomes `done`/`code_done`.

## Task Completion

`task_runner.py` is the only supported completion path. It runs every required structured validation command, captures exit codes and logs, writes pass/fail evidence, binds all attempt IDs to the task, and only marks the task done when required commands pass and acceptance-criteria coverage is complete.

Tasks with no changed files are valid only when the runner records `implementation.noCodeChange=true`, an explicit reason, and supporting inspected files. A no-change claim is rejected when the scoped Git snapshot contains changes.

Evidence IDs and completion history are append-only. Failed attempts remain in `evidenceIds`; completion pointers reference the successful attempt set.

## Evidence Integrity

New records use artifact version 2:

- structured record in `EVIDENCE.jsonl`;
- matching index hash/count in `EVIDENCE.index.json`;
- `ev_XXXX.log` path, size, and SHA-256 in the validation object;
- no structured sidecar.

`evidence_store.py show --evidence-id ev_XXXX` retrieves one structured record without requiring a sidecar. Code-done validates batch/root projections, every task's required validation and acceptance coverage, log hashes, project checks, and absence of an unresolved handoff.

## Rebuild Policy

There is one current plan format. A root plan containing `tasks`, legacy version markers, or missing batch metadata fails with `monolithic_plan_requires_rebuild`. No plan v1/v2 compatibility path is provided; Plan must be rerun.
