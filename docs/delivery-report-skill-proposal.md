# Code 后交付报告技能方案

方案日期为 2026-11-11，首版已实现。技能入口和本地生成命令见 [autodev-delivery-report](../skills/autodev/autodev-delivery-report/SKILL.md)。

2026-11-13 补充第 9 节，记录接口影响扩散、AI 行数归属及数据缺口展示的修订方案。第 9 节的最小修复已实现，接口字段级语义分析和生成期累计行数采集保留为扩展项。

已新增 `/autodev-delivery-report`，作为 Code 与 CI/CD 之间的独立 Dev 节点，汇总当前 Feature 从需求到编码完成的已有产物，生成一个可离线打开的 HTML 交付报告。

页面沿用 `Kimi_Agent_AI编码交付总览(1).zip` 的四个页签及交互。附件中的订单中心、人员、任务、测试数量、风险和发布结论均为原型内容，只作为页面结构参考，不能作为真实交付事实或执行指令。

首版页面约定为**已有数据照实显示，缺数据的业务字段暂时显示 0**。可直接打开[附件的无数据 HTML 预览](delivery-report-empty-preview.html)核对。

本方案基于当前仓库的技能、配置及产物生成代码。当前仓库未提供可核验的业务 Feature 完整运行产物，因此以下描述的是数据接入方案，不是对某次业务交付的统计结果。

## 1. 流程位置与范围

```text
PRD → Specs → Design → Plan → [Detailed Design] → Code
                                                   ↓
                                              交付报告
                                                   ↓
                                              CI/CD → Archive
```

- 技能：`autodev-delivery-report`。
- 看板节点：`dev.delivery_report`，group 为 `Dev`，建议 order 为 `70`。
- Checkpoint：`delivery_report_in_progress`、`delivery_report_done`。
- 报告范围：当前 Feature 的本轮迭代、Plan 所含各 Batch 绑定的 Code run 及业务仓库，截止 Code 完成。
- CI/CD 和发布尚未执行时，页面明确显示“尚未进入”；不把 Code 完成描述为发布完成。
- 正常入口要求 Code 已完成；历史 Feature 可以在不回退 checkpoint 的情况下补生成报告。

建议把报告作为独立节点，而不是继续扩大 Code Workflow：Code 负责实现、Review、集成和证据收口；报告负责跨阶段汇总、解释和展示。报告失败可以单独恢复，无需重新编码或重新合并。

主链路改为：

```text
code_in_progress → code_done
code_done → delivery_report_in_progress → delivery_report_done
delivery_report_done → cicd_in_progress → cicd_done → archived
```

当前 `skills/references/ui-continuation-guide.md` 规定阶段完成后通过项目看板开启下一阶段会话。本期保留该交接方式：Code 完成后的看板下一步变为“交付报告”，固定 Workflow 不直接启动下一技能。若以后需要同一会话连续执行，应单独调整共享交接协议。

## 2. 输入：复用哪些现有产物

| 已有产物或事实 | 报告用途 | 使用方式 |
|---|---|---|
| `read_state_json.py` 输出 | Feature、当前 checkpoint、流程选择 | 使用现有状态读取入口，不手工改写状态 |
| 有效 workflow 配置 | 阶段顺序、被选中/跳过的节点 | 使用编译后的当前 Feature 契约，不能只按静态标准链判断 |
| `PRD.md` | 背景、目标、范围、业务验收要求 | 提取业务摘要；缺失字段显示 0，记录缺少 PRD |
| `proposal.md`、`specs/**/*.md` | 能力、需求、Scenario | 提取需求与行为边界，建立到任务的追溯 |
| `design.md`、`.design-contract.lock.json` | 架构决策、约束、接口设计 | 用于解释设计依据；设计内容不能证明代码已实现 |
| `UI_CONTEXT.json`、可定位的 `FRONTEND_ROUTE.json` | UI 范围、前端实现模式 | 辅助页面归类，不作为已交付页面数量 |
| 根 `plan.json` 和 `plans/<batchId>/plan.json` | Batch 索引、完整任务、依赖、需求引用、执行状态与交付绑定 | 用 `hooks.plan_json.load_plan_bundle(feature_dir)` 读取根索引列出的 Batch 文件，按返回的 tasks 和 task_batches 统计 |
| `DETAIL_DESIGN.md` | 文件级设计说明 | 可选，未开启详细设计不记为异常 |
| `evidence/EVIDENCE.jsonl` 及其引用产物 | 实现细节、文件变更、生产编译、任务证据 | 只读提取，保留 evidenceId、任务和仓库绑定 |
| `.parallel-runs/<runId>/manifest.json` | Batch 状态、Review 状态、仓库绑定、合入、遗留问题、工作区同步 | 按 Batch 的 deliveryRunId 读取所属 run，核对 mergeCommitSha |
| `.parallel-runs/<runId>/final-evidence-aggregate.json` | 最终证据审计结果 | 复用现有结论，不重新执行具有状态写入副作用的 aggregate |
| Review 的 `stageStates.review.evidencePath` | Review 发现、处置情况、残留问题 | 按 manifest 的引用解析，不猜测固定报告文件名 |
| Evidence 中生产编译记录 | 命令、退出码、源码摘要、日志位置 | 独立显示为生产编译，不计入自动化测试 |
| TASK 执行记录中 `frontendVerificationPath` 指向的记录 | 前端检查、视觉检查与截图 | 按实际引用读取；不能推断为 E2E 通过 |
| run 仓库的 `baseSha`、`headSha` 及只读 Git diff | 实际文件、增删行数、接口和路由变更核对 | 基于封存交付范围，不对用户当前脏工作区做全量统计 |
| `FEATURE_API_DETAIL.md` | 接口说明及代码位置 | 可选；它由独立产物同步技能生成，当前 Code 不保证产出 |

标准报告读取 Plan bundle、Evidence、Batch 绑定的 manifest 和最终 aggregate。独立 aggregate 文件缺失时，核对同一 manifest 内的 `finalEvidenceAggregate`。历史 run 只有 `finalVerification` 时显示原验证结果，审计字段按缺数处理。已定位到正确 Feature/迭代时，历史缺件或被跳过的环节可生成带缺口的报告。上游被合法跳过、没有 UI、没有详细设计等情况按实际 workflow 展示，不要求重跑前置阶段来补文档。

这几个来源需要特别区分：

1. `plan.json` 表示计划与任务状态，Evidence 和 runtime 表示执行、Review 与交付证据，两者应交叉核对。
2. `validation-summary.md` 是现有的人类可读投影，还保留 UTest 列，不适合作为新报告的数据源。
3. `FEATURE_API_DETAIL.md` 不是报告前置门禁；缺少它不应自动触发上传或同步。
4. 仓库里保留的旧测试技能、历史文档或测试夹具，不能证明当前 Feature 执行过测试。

## 3. 页面：保留原型四个页签

### 首版缺数据的统一显示规则

| 字段 | 无数据时的显示 | 有部分或完整数据时的显示 |
|---|---|---|
| 接口、页面、AI 生成行数、任务、测试、风险、发布检查计数 | `0`，保留“个、行、项”等单位 | 每项独立取值。已有 5 个已交付任务且无覆盖率时，分别显示 5 和 0% |
| 百分比、分子/分母、图表 | `0%`、`0 / 0`、零长度圆环或进度条 | 分子与分母各自沿用实值。分母缺失或为零时百分比显示 0%，单独保留分母原因 |
| 原型中的负责人、仓库、分支、提交号、版本、构建号、说明等业务字段 | 单个缺失值显示 `0` | 已知名称、真实生成时间、业务文本和代码标识原样显示 |
| 任务、变更、用例、风险与明细表 | 数量 0，集合为空，可显示“共 0 项” | 只展示实际记录，没有记录的筛选项仍可点击 |

置零规则适用于左侧决策栏、页签角标、卡片、图表、表格、筛选数字、抽屉、辅助阅读标签和导出的 Markdown 摘要。标题、列名、单位和操作按钮照常显示。原型中的“1 项 P0”“2 / 4 通过”等示例，以及藏在 aria 标签、进度条宽度和导出文件名中的订单数据，都从同一份报告数据替换。

采集层保存原始值、来源及可用性。展示层遇到无值时才生成 0。已核验的真实零保留来源，缺数零在页内注明“缺失字段暂按 0 显示”，详情或来源说明给出原因。计算比率时使用原始值。发布检查的通过数只累计有明确通过证据的项目，分母明确为已评估项数。所有检查都缺证据时，左栏显示“0 / 0 已评估项通过”，状态为“待评估”。筛选后的空列表与已完成检查且发现 0 个问题分别记录。

### 3.1 交付总览

保留原型的结论区、指标卡、完成率、风险入口和模块变更分布，内容改为：

- Feature 名称、项目、runId、生成时间、截止阶段与代码版本。
- 一句话交付摘要：完成了什么、还缺什么、证据是否完整。
- 阶段产物时间线：PRD、Specs、Design、Plan、可选详细设计、Code、Report；每项可查看产物摘要和来源。
- 接口与页面实际变更数量，分别展示新增、修改、删除；无法确认的数量显示 0，并在来源说明注明待核验。
- 代码变更行数：新增、删除、净增，按仓库或模块展开。
- Plan 完成情况、质量证据概况、重点风险。
- Batch 集成情况与用户工作区同步情况，分别展示；不能把集成成功等同于用户目录已同步。

保留原型“AI 生成代码”指标。存在与本次交付绑定的累计生成行数记录时填入实值。缺少累计记录时，自动取已交付 AI TASK 涉及源码在基线至交付提交中的新增行，按仓库文件去重，并在页面标注口径。任务证据或 Git 对象不可用时显示缺口。Git diff 提供的新增、删除、净增以各自的指标名显示。

### 3.2 Plan 任务

保留筛选、表格和详情抽屉，增加当前流程需要的状态区分：

- 未开始、进行中、已实现、已交付、阻塞、已跳过、状态待核验。
- 每个任务展示 outcome、所属 Batch/仓库、需求与 Scenario 引用、交付状态、证据和关联风险。
- 把“计划覆盖的 Scenario”与“已测试的 Scenario”分开，不能用任务声明的 refs 证明测试通过。
- 待确认风险是独立维度，不能与未完成任务相加。
- 没有真实人员信息时，负责人显示 0；Batch 或 Agent 标识单独展示。

总览优先展示“交付完成率”：已完成集成且存在匹配证据的任务数 / 当前纳入交付范围的任务数。未匹配的任务不计入已交付；分母为零时完成率显示 0%。实现率可以作为辅助指标，并明确统计口径。

### 3.3 测试质量

保留原型页签，但改成能够反映现行 Code 策略的证据展示：

| 指标 | 当前默认展示 | 何时可以显示真实数值 |
|---|---|---|
| 生产编译 | 各后端任务已登记的结果与日志 | Evidence 绑定当前 TASK/run 和对应源码 |
| Batch Review | 通过、定向修复接受、遗留问题等原始结果 | 对应 Batch 的当前 Review Evidence 有效 |
| 前端检查 | 工程检查、视觉检查及证据缺口 | 存在匹配当前交付的前端验证记录 |
| 单元测试 | 0 个，注明当前流程未执行 | 已有外部/历史结果能确认绑定本次交付版本 |
| E2E | 0 个，注明当前流程未执行 | 已有外部/历史结果能确认绑定本次交付版本 |
| 行/分支覆盖率 | 0%，注明缺少结果 | 存在可解析且版本匹配的真实覆盖率报告 |

当前 `autodev-code/SKILL.md` 和 `parallel_evidence_aggregate.py` 已明确：Code 不执行 UTest/E2E，最终 aggregate 只审计已有交付与 Review 证据。因此报告不得沿用原型的 86 个单测、18 个 E2E、82.4% 覆盖率等数字，也不应自动补跑测试。

无测试产物时，页面显示单测 0、E2E 0、未测试 0、行覆盖率 0%、分支覆盖率 0%、用例执行覆盖率 0%。保留缺数状态供摘要和门槛判断使用。存在已匹配的用例计划和执行记录时，按用例 ID 对账统计未测项。

### 3.4 重点风险

保留架构、安全、API、复杂度四类入口，并容纳实现未完成、证据不完整、工作区同步等交付问题。

- 事实来自 Review findings、`deferredIssues`、aggregate errors、实际 API 差异与已有检查结果。
- 展示来源、原始严重程度、当前处置、关联任务/文件、建议动作。
- 已修复、已接受、仍开放、待核验分别展示，保留其来源证据。
- 已被定向修复的 Review 问题不能仅因旧记录仍在就重复计为开放风险。
- 无安全扫描或复杂度数据时数量显示 0，状态标为“未评估”；有检查结果且未发现问题时才显示“本次检查未发现”。
- 模型可解释已有风险、给出建议；新增推断必须标为“待核验建议”，不能冒充已发现漏洞或擅自补出 P0 等级。

页面的结论围绕编码交付、质量证据和待办事项展开。若展示发布建议，应说明依据与缺口；报告生成成功不授予发布权限。

## 4. 生成方式：脚本计算事实，模型组织说明

```text
读取当前 Feature 状态和有效契约
                ↓
按迭代及 Batch 绑定定位 run 和每个仓库的交付版本
                ↓
脚本收集并计算结构化事实
                ↓
模型生成阶段摘要、业务说明和风险建议
                ↓
校验事实引用与统计一致性
                ↓
固定模板渲染单文件 HTML
                ↓
发布 HTML + JSON，通过产物门禁后推进 checkpoint
```

技能职责是编排、解释与交接；重复计算、格式转换和数据校验放入脚本。避免每次让模型重新写整页 HTML，保证页面稳定且各处数字一致。

### 4.1 确定统计快照

- 用状态记录定位 Feature 与迭代。活动产物在 `.autobizdevops/features/<feature>/`，已归档迭代在 `.autobizdevops/archive/<feature>-iter<N>/`。归档内的绝对 Evidence 路径已移动时，按原 Feature 相对路径在选定迭代内重定位并核对 ID/digest。
- 按 Plan bundle 中每个 Batch 的 `deliveryRunId` 和 `mergeCommitSha` 对账 manifest。与 `hooks/evidence_integrity_gate.py` 的交付校验一致，合法的多个 run 可各自贡献所绑定的 Batch。记录每个任务的归属，同一任务或重试记录只计一次。归属有歧义的项标为缺口，可展示其他已核验项。不能唯一定位 Feature 或迭代时才要求选定作用域。
- `production_compile` 的 `Evidence.runId` 是任务执行 ID。`.task-runs/<taskId>/<taskRunId>.json` 中的 `parallelRunId` 才指向 Code run。以 Plan 的实现/完成 Evidence 引用、对应任务执行记录及当前源码摘要关联编译记录和前端验证，防止漏算或采入旧尝试。
- Code 已完成且仍有 `workspaceSyncPending`、`cleanupPending` 时，保留并如实展示，不重新启动 Workflow。
- 为输入产物记录相对路径、hash、runId、Plan 修订和交付 SHA；采集前后检查快照一致性，遇到并发变动则重试或停止发布。
- 指纹排除报告自身 checkpoint 推进、生成时间等字段，防止报告发布后立即被自己的状态变化判为过期。

### 4.2 结构化数据与模型补充

建议最终 JSON 至少包含：

```json
{
  "schemaVersion": "autodev.delivery-report.v1",
  "featureId": "<当前 Feature>",
  "runIds": ["<Batch 绑定的 Code run>"],
  "scope": { "throughStage": "code" },
  "snapshot": {
    "planRevision": "<实际修订>",
    "inputDigest": "<输入快照摘要>",
    "repositories": []
  },
  "generationStatus": "generated_with_gaps",
  "deliveryStatus": "<按实际证据派生>",
  "stageArtifacts": [],
  "metrics": {},
  "tasks": [],
  "quality": {
    "unitTests": {
      "status": "not_executed_by_workflow",
      "passed": null,
      "total": null,
      "displayPassed": 0,
      "displayTotal": 0,
      "reason": "当前 Code Workflow 不执行单元测试"
    },
    "lineCoverage": {
      "status": "missing",
      "value": null,
      "displayValue": 0,
      "unit": "%",
      "reason": "未提供匹配交付版本的覆盖率结果"
    }
  },
  "risks": [],
  "workspaceSync": [],
  "sources": [],
  "gaps": [],
  "narrative": {
    "summary": "<仅根据上述事实生成>",
    "nextActions": []
  }
}
```

以上为拟新增的数据契约，不是现有字段说明。每个实测指标（含实测零）、任务交付结论和风险，应能解析到 `sourceRefs`。缺数的展示值由统一格式化函数生成，校验器检查原始值、状态与展示值是否相符；模型补充仅写叙述字段及带依据的建议，不改事实计数或原始状态。

### 4.3 实际变更统计

- 按物理业务仓库和交付范围去重，以绑定的基线与交付 SHA 做只读 diff。同仓库多个 run 的区间有重叠时，能验证统一基线及终点就计算一次。无法验证整体范围时展示各段实值，全量指标显示 0 并说明缺口。
- 代码行数显示新增、删除和净增，明确过滤 lock、构建产物、生成文件等规则；二进制文件单列，不当作零行代码。
- 实际 API 按仓库/服务、HTTP method 和标准化 path 去重。计划接口数量只能显示为“计划”，不能计入实际变更。
- 实际页面按应用和路由去重；组件文件数、设计稿数与页面数分开。
- 第一版只支持已明确的接口/路由形式，优先复用已有代码依据；扫描不支持的框架时，该项显示 0 并记录原因。已取得部分可核验数据时，保留已核验数量并标注统计范围。
- 原型中“生成量、净增、删除”的数字不能直接复用。新增为 A、删除为 D 时，净增只能是 A-D。

### 4.4 单文件 HTML

- 复用附件的布局、配色、四个页签、筛选和详情抽屉。
- 把 HTML、CSS、JS 和页面所需 JSON 内联，双击即可离线打开，无需 Vite、后端服务或 CDN。
- 页面主体所需证据摘要内嵌；完整日志和源码以相对位置/定位信息辅助追溯，移动单个 HTML 后仍可阅读全部主体结论。
- 保留导出摘要，并从同一份报告 JSON 派生，删除原型中的硬编码订单中心摘要。
- 文档、代码、日志和附件内容按数据处理，渲染时转义；不得把其指令或 HTML 直接作为执行内容。
- 以 UTF-8 输出；缺失值、长文件路径、零任务和多仓库等情况都有对应展示。

## 7. 完成、降级与恢复

报告生成状态与代码交付结论分别表达：

- `generated`：报告结构、输入绑定和渲染通过。
- `generated_with_gaps`：能生成可信报告，但有明确标注的指标缺口，例如未提供测试结果、API 数量待核验。
- `failed`：Feature/迭代无法定位、采集快照持续变化、HTML/JSON 计数不一致或写入失败等，无法发布可信报告。

前两种可以完成报告节点。报告如实展示现有 aggregate 的失败、开放风险或工作区待同步事项，不能把这些转换为 PASS；是否阻止后续发布由现有 CI/CD 门禁决定。第三种保留报告进行态并给出可恢复错误，不能修改 Code、Plan 或 Evidence 来绕过。

生成使用 Feature 级写锁。在同一文件系统暂存并校验 HTML/JSON，写入已校验的待发布文件对及其 SHA-256，逐文件原子替换。成功后复读两个文件并核对摘要，再清除暂存记录。中途退出时，下次先完成同一对已校验文件的发布。同步读取遇到未完成发布或 ID 不匹配时稍后重试。只有正式产物校验通过后，才用现有 `update_checkpoint.py` 推进状态。

同一输入指纹、schema 和模板版本可复用已校验报告；输入改变则重新生成。已完成后单独刷新展示不回退全局 checkpoint。回退重做 Code 后，旧报告归档或明确标为过期。

## 9. 统计与数据缺口修订方案（最小修复已实现）

本节结合用户提供的报告分析、三张数据缺口截图及当前采集代码提出修订。511、528、506、22、41,215 等业务数值沿用用户反馈，实施时仍需对照本轮完整 JSON 和封存 Git 差异复核。

当前最小实现使用现有静态解析和 Git 证据，已落地接口实现/契约/待核验影响分列、路径与快照归属恢复、Batch 区间回退、诊断聚合、Pages 与子组件识别、本地 Mapper 片段和 include 解析，以及展示和导出统一。字段级实际使用、复杂重载与动态调用的语义确认、生成阶段累计行数写入仍属于扩展范围，无法确认时保留覆盖说明。

### 9.1 接口实现变更与依赖影响

当前 `source_index.py` 将方法、类型及可达依赖的内容共同计算指纹，并从整个类的类型引用继续扩展依赖。`changes.py` 把这些指纹变化统一登记为 modified，共享 DTO 变化会扩大主卡计数。仅凭 affectedFiles 包含某个 DTO，还无法确认入口实际使用了哪些变化字段。

修订后的判断如下。

| 可核对的证据 | 归属 | 主卡处理 |
|---|---|---|
| 新增或删除 HTTP 入口 | 接口新增、删除 | 计入对应数量 |
| Handler 方法体发生变化 | 接口实现修改 | 计入修改数量 |
| 入口实际调用的 Service 方法或 Mapper SQL 发生变化 | 接口实现修改 | 保留调用链及修改位置后计入 |
| 请求或响应中实际使用的字段结构变化 | 接口契约影响 | 展示独立影响数量及字段依据 |
| 共享类型、公共类或无法确定目标的传递依赖 | 待核验影响 | 在影响明细中展示 |

实施要求如下。

- 为方法调用、参数类型、返回类型及普通类型引用记录不同的关系，保留入口到具体修改位置的追溯。
- 按实际调用的方法、重载目标和 SQL statement 比较。DTO 字段分析需要确认请求、响应使用范围。无法定位的关系进入识别覆盖说明。
- 使用 Plan、实际交付文件和服务模块定义核对本期范围。跨模块的显式变更仍可计入，公共类型关联的跨模块影响单列。
- 按仓库、服务、HTTP 方法和标准化路径去重，保留 Controller、方法及代码位置。相同服务中的路由冲突给出具体诊断。
- 总览、模块分布、详情与摘要导出复用同一份入口集合。用户提供的约 22 条业务入口作为重点核对清单，数量通过重算确定。

### 9.2 AI 行数自动恢复与正常零值

当前回退统计直接匹配任务 changedFiles 与 Git 相对路径，尚未充分使用工作区前缀、运行记录中的仓库映射和 fileChanges。原始路径形态不同会造成归属失败。现有 verified_existing 分支已支持无变更任务，还需要统一历史执行模式及明确的 noCodeChange 标记。

依次使用以下来源恢复归属。

1. 读取版本匹配的已有生成统计，并保留累计生成或交付新增的原始口径。
2. 从实现 Evidence 的 fileChanges、changedFiles 及任务执行记录归一化逻辑仓库 ID、仓库相对路径和重命名路径。
3. 结合 Batch 封存提交、任务运行快照和可确认的 AI 执行范围恢复文件集合。任务归属不足时，允许有明确来源的 Batch 级统计，并注明范围。
4. 汇总可核验的源码行数，逐项保留无法恢复的任务、原始路径、转换后的路径及失败原因。

明确的验证已有实现、无代码变更任务贡献已确认的 0 行。缺少任务文件清单时先核对模式和上下文，再判断是否缺件。一个任务缺件时保留其他任务的已核验数量，状态为 partial。

排除运行目录、`.frontend/html-analysis`、日志、报告、依赖、构建输出及其他生成材料后计算业务源码新增、删除和净增。重试、修复及多任务修改同一文件按最终交付区间去重。文件归一化保持 Git 原始路径大小写，以仓库身份避免多仓库同名路径混合。

默认指标使用“AI 交付新增行”，表达最终交付保留的、可归属 AI 执行的新增源码。累计生成行数继续读取真实上游记录。另行展示全部交付源码的增删统计及各自来源。

后续由插件的任务收口或 Batch 封存脚本，将仓库、基线、提交、源码增删和统计口径写入现有 Evidence，报告自动读取。

### 9.4 数据状态与诊断分类

指标保持原始 value、displayValue、来源和状态。是否生成缺口由来源有效性、阶段预期及解析结果决定，reason 有文字本身只承担说明作用。

| 情况 | 指标及诊断处理 | 页面位置 |
|---|---|---|
| 必需产物不存在、损坏或版本绑定失效 | missing，登记真实数据缺口 | 数据缺口 |
| 已取得部分有效数量，部分入口无法核对 | partial，保留已核验实值，登记识别覆盖说明 | 指标说明与识别覆盖 |
| 内部 Service、Mapper 或子组件已识别，但无需作为独立入口 | 保留所属模块、调用或引用关系 | 变更明细 |
| 某内部文件暂未连到入口，且没有缺少必需来源的证据 | 登记待分析范围，注明对指标的影响 | 识别覆盖 |
| Code 按有效流程未执行 UTest/E2E，且本轮未要求提供对应外部结果 | 业务字段显示 0，并注明本阶段未采集 | 质量说明 |
| UI、详细设计等阶段被合法跳过或本轮不适用 | 显示 0 或已跳过，记录流程依据 | 阶段说明 |
| 完成核对且实际发现 0 项 | measured，value=0，保留来源 | 对应指标 |

测试计划或明确要求的外部结果缺失时，仍登记实际缺口。生成状态根据真实缺口和影响报告可信度的覆盖不足决定，同时保留分类摘要。正常跳过、未采集说明和合法内部文件本身均有对应状态。

### 9.5 聚合、展示和历史兼容

采集层为诊断提供稳定标识、reasonCode、category、scope、affectedMetrics、affectedFiles、sourceRefs 和 nextAction。scope 包含迭代、仓库及运行身份。文件清单作为数组保存。

先按根因、类别、仓库、迭代、运行及相关来源对象聚合，再合并关联指标与文件。不同运行、不同损坏文件及不同问题保留独立身份。同一原因关联 api、apiAdded、apiModified、apiDeleted 时，只生成一条诊断，各指标引用该诊断的标识。

新增、修改、删除分别通过基线和交付版本入口清单确认。只有确实无法判断的维度标为 partial 或 missing。已确认的数量继续展示，共享类型影响按 9.1 单列。

页面调整如下。

- “数据缺口”只统计去重后的真实缺失或无效来源，字段显示中文名称和具体仓库、Batch、任务范围。
- “识别覆盖说明”单独折叠，概述未解析的入口或关系、已识别范围及下一步核对动作。
- 本阶段未采集、合法跳过和不适用项目在对应阶段、指标内说明。
- 列表展示问题摘要、范围、关联指标和建议处理。长路径显示关联文件数量，展开后查看完整列表和来源。
- 同一主因在详情中列出受影响指标，减少重复文件段落。原始文件路径完整保留，包含中文目录和实际大小写。
- 页面计数、指标详情、JSON 和摘要导出共用聚合后的诊断数据。

历史报告的 `{field, reason}` 保留读取兼容。历史缺口无法可靠分类时标为待复核，保留原原因，重新采集后生成结构化分类。迁移过程保留可追溯信息。

## 11. 接口实际变更口径与视觉调整（已实现）

本节更新第 9 节中契约影响从主卡剔除的旧口径：已确认输入输出契约变化也属于接口修改。接口总数按仓库、HTTP 方法和路径去重，合计新增、实现链路修改、契约修改和删除。实现链路与契约同时变化时只计一次；只有潜在依赖关联的候选仍单独待核验。

“Controller 只有一个方法变化，所以接口修改 1 个准确”的结论不成立。Service、辅助方法、Mapper SQL、实际引用常量等变化，应通过调用链关联既有入口；Controller 文件无需修改。1 条实现变更、1 条契约变更和 4 条潜在影响，也不能直接断言实改正好为 6：需要逐一确认 4 条候选，且可能仍有未定位的纪要等入口。

补充隐式 public 接口和 Mapper 成员、包级方法、继承、方法引用、链式调用、按参数数量/已知类型判定重载及可定位的命名注入。按同模块和导入匹配类型，保留具体实现变更证据，新增未使用枚举常量不扩大接口实改数。测试覆盖 Controller 无变化而 5 条实现链路与 1 条契约变化合计 6 个接口。动态分派及歧义目标继续给出 partial，保留已有实值。

页面采用深蓝交付结论区、蓝色接口指标、青色页面指标和紫色 AI 指标。绿色用于通过/已修复，橙色用于待核验/待办，红色用于失败/阻断，契约修改使用紫色标签。内容分组卡片、简化来源按钮、可追溯调用链及手机记录卡片替代密集长路径表格。
