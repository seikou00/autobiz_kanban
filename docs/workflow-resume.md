# Workflow 中断恢复

Workflow 默认在同一 run 内持续恢复，没有整体重试次数上限。失败后按持久化阶段状态续跑，
不会通过新建 run、重做已完成 TASK 或跳过 Review 来推进。

- 调度轮询自动重新检查旧的 `blocked/failed` Batch，以及执行者已经失联的活动阶段。
- 尚未完成的阶段保留 worktree、提交与证据，重新派发后继续执行。
- Review 已经完成但返回丢失时，保留已有结论并接续交付，不重新实现或评审。
- 已有合并或同步回执时复用其结果；同步失败不重新打开已合并的 Batch。
- 调度读取、准备、汇总、完成登记与工作区同步的瞬时失败持续退避重试。
  汇总已完成、仅完成登记失败时，只重试登记。
- 派发领取返回丢失时用相同请求 ID 重试，复用原 owner token；完成和失败登记也使用
  原派发代次及 token 重试，避免遗留无人接续但仍占用名额的有效派发。

短期局部尝试和等待窗口仅用于让出执行机会，不会耗尽整个 Workflow 的恢复次数。
调度和控制恢复等待最多 30 秒一轮；工作区同步按 5、30、120 秒退避，之后保持 120 秒。
较新的累计同步目标可以覆盖处于退避中的旧目标，但必须以实际成功回执和 Git 祖先校验为准。

恢复前仍检查工作区、分支、提交和任务绑定。有效派发或业务租约不会被其他恢复者抢占，
旧派发代次的迟到回写会被拒绝。真实实现缺陷继续进入修复，不能因重试次数多而标记通过。
缺少有效 Review 回执时只重新打开 Review，保留实现进度。运行状态锁默认等待最多 30 秒，
超时后交给恢复循环重试；不会通过删除锁文件抢占其他执行者。

权限、网络、仓库完整性等前置条件持续不满足时，保留错误和现场并继续重查；重试本身不能
代替修复外部环境。宿主关闭后不在后台脱管运行，重新启动 Workflow 时复用原 run。
主动取消、回滚和已清理的 run 保持终止状态。
